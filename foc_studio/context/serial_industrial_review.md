# 串口模块工业级 Code Review

审查日期：2026-09-14  
审查范围：`lib/services`、`lib/protocol/pc_mcu`、`FocController` 及其页面接入点。

## 1. 现有架构

当前主链路为：

```text
UI / FocController
        ↓ 跨 isolate 请求、低频快照
SerialPortService（UI isolate 代理）
        ↓
serial-session isolate
        ├─ SerialTransport：端口枚举、打开、配置、读写、物理连接状态
        ├─ PcMcuProtocolClient：增量解帧、CRC、消息编解码、有序发送队列
        └─ FocSession：心跳、周期控制、设备状态、时间对齐、有界历史
```

这个分层适合作为后续工业化基础，不需要整体重写。高频原始字节未经过 UI
isolate，半帧跨块保留，发送支持短写续传，后台状态与页面可见性解耦，这些方向是
正确的。

## 2. 问题与风险分级

### S0：必须在设备联调前明确的安全风险

1. `connected` 目前只代表本地端口打开，没有“MCU 在线 / 数据新鲜 / 协议可用”状态。
   USB 转串口仍在但 MCU 卡死时，UI 可能长期显示已连接。
2. 主动断开没有先完成受确认的安全停机，只能依赖 MCU 2 秒控制看门狗。重启 MCU
   时，`FocSession` 仍保留之前的使能目标，周期控制可能在重启后再次发送使能。
3. 参数写入没有 ACK、事务号、超时和失败码。紧随其后的读回只能看到某个响应，无法
   证明它属于本次写入，也不能区分写入拒绝、响应丢失和旧响应迟到。

这些问题需要 PC 与 MCU 一起定义语义，不能由上位机单方面把“已入发送队列”包装成
“执行成功”。

### S1：高风险可靠性问题

1. 原发送队列在非阻塞写持续返回 0 时会永久每 5 ms 重试，连接状态不变，周期命令
   继续积压。本轮已增加单帧 1 秒截止时间并在超时后断开。
2. `SerialPortConfig` 原来在交给 `SerialPort` 后立即释放；依赖实现还会在
   `SerialPort.dispose()` 中再次释放缓存的 config。非 Windows 存在重复释放路径；
   Windows 为规避崩溃跳过 port dispose，又会泄漏 native port 对象。本轮已修正
   config 所有权；Windows port 对象释放仍需真机压力验证后解决。
3. 发送写入原来只把 `SerialPortError` 当作传输失败，其他 write 异常只会清队列而
   保持假连接。本轮已统一把编码完成后的 write 异常判为传输失败。
4. 除扫描外，跨 isolate 的连接、断开和业务请求没有截止时间。如果底层调用卡住，
   Future 与 busy 状态会永久等待。超时还必须配套“迟到操作撤销”，不能只在 UI
   Future 上简单加 `timeout()`。
5. 当前业务 UI 尚未接入：`FocController` 在 `MainPage` 中创建后没有传给
   `MotPage`，也没有监听者触发业务快照；`MotPage` 明确仍是静态页面。
6. 当前 `test` 目录没有测试文件，既往运行过的临时测试不能作为持续回归保护。
   本轮曾补充并通过 18 项测试，测试代码随后已按要求删除，仅保留历史验证结论。

### S2：中风险诊断与演进问题

1. 协议错误只保留最后一条字符串，没有时间、命令、原始长度、连续错误次数等结构化
   上下文。
2. 未知命令允许 0～255 字节；若噪声把命令或 LEN 破坏成未知长帧，解码器会等待该
   候选长度，可能推迟后续好帧的重新同步。需要结合协议版本策略决定是否允许未知帧。
3. Hall A/B/C、`hall_state`、`electric_sector` 原来没有交叉校验。本轮已按协议加入
   一致性校验。
4. 四类遥测共用一个 MCU tick 同步器。跨消息源乱序、MCU 意外复位和长期晶振漂移的
   行为尚未定义；波形功能上线前应改为会话级 tick 展开加每通道单调性检查。
5. 后台 isolate 失败后会正确进入 failed，但不会自动重建。工业现场是否自动恢复需
   配合重连退避、最大次数和人工确认策略设计。
6. 历史队列在后台持续维护，但当前没有分页/增量读取接口；后续波形不应重新把完整
   历史塞回 20 Hz 普通快照。

## 3. 目标架构（增量演进）

保留现有五层，新增以下职责：

1. **连接健康模型**：区分 `portOpen`、`protocolOnline`、`degraded/stale`、
   `disconnecting` 和 `failed`；以最近有效帧及关键响应为依据，不以 `isOpen` 代替
   设备在线。
2. **发送调度器**：每帧截止时间、队列水位、连续零写计数；周期心跳和重复控制命令
   可合并，人工控制命令优先于低优先级查询，但绝不插入已开始发送的帧中间。
3. **请求事务层**：协议增加 sequence/request-id、ACK/NACK、错误码；PC 维护单次请求
   的超时、有限重试和响应匹配。参数写入使用“校验 → 写入 → ACK → 查询 → 值比较”
   状态机。
4. **诊断事件流**：结构化记录连接代次、命令、错误类别、队列深度和时间；日志落盘
   与 UI 展示分离，并设置文件轮转上限。
5. **历史数据接口**：为图表提供按游标/时间窗增量读取或共享环形缓冲，不扩张普通
   `FocSnapshot`。

## 4. 分阶段修改计划

### 阶段 A（本轮已完成，不改变 MCU 协议）

- 修正 `SerialPortConfig` 所有权，避免重复释放。
- 非阻塞写增加单帧 1 秒截止时间，超时清队列并关闭当前连接。
- 任意发送异常都使当前传输失效。
- Hall 状态增加协议内一致性校验。
- 曾以 18 项协议、分包、CRC、时钟、短写和发送超时测试验证本轮修改；测试代码
  随后已按要求删除。

### 阶段 B（下一轮，仍可只改 PC）

- 增加协议在线/数据陈旧状态和 UI 指示，不立即自动重连。
- 给跨 isolate 操作增加分操作截止时间、连接代次和迟到结果抑制。
- 周期帧去重/合并；暴露队列水位、最长等待时间和连续零写统计。
- 将 `FocController` 注入 MOT 页面，先接入只读状态，再接入受保护的控制操作。

### 阶段 C（需要同步修改 MCU 协议）

- 增加 request-id、ACK/NACK、设备错误码和能力/协议版本协商。
- 实现参数写入事务和读回比对；UI 只在事务完成后显示成功。
- 定义停机、断连、重启的安全状态机以及谁拥有最终控制权。

### 阶段 D（长期运行能力）

- 波形增量读取、日志文件轮转、故障事件快照。
- 自动重连退避、端口身份识别（VID/PID/序列号）和连接冲突处理。
- 8～24 小时吞吐与反复插拔压力测试，监控 native handle、内存和 isolate 数量。

## 5. 测试方法

### 自动测试

当前仓库可直接执行静态检查和构建：

```powershell
flutter analyze --no-pub
dart format --output=none --set-exit-if-changed lib
git diff --check
flutter build windows --debug --no-pub
```

本轮删除前的 18 项临时测试曾覆盖：所有分包边界、粘包与噪声、已知命令坏 LEN、
CRC 错误恢复、尾部单字节帧头、控制命令字节序/范围、Hall 语义校验、MCU tick
对齐/回绕/复位、短写、一次零写恢复和发送截止时间熔断。因为测试源码已删除，后续
修改不能依赖这些历史结果作为持续回归保证。

### 虚拟串口测试

1. 使用成对虚拟串口运行 MCU 模拟器，注入随机分包、粘包、CRC 错误、延迟和丢帧。
2. 将接收频率提升到目标值的 2～5 倍，持续至少 1 小时，确认 UI 无卡顿、队列不增长。
3. 模拟写端停止读取，验证 1 秒内连接进入错误状态且旧队列不会带入重连。
4. 随机重启模拟 MCU，验证旧 tick、旧参数回复和旧业务状态不会污染新会话。

### 真机验收

1. 电机未使能、已使能、调参写入三个场景分别执行拔线、MCU 复位和上位机退出。
2. 重复连接/断开至少 1000 次，观察 Windows 进程 handle、private bytes 和 isolate 数量。
3. 8～24 小时持续运行，记录 CRC 率、无效帧率、队列峰值、最大消息间隔和日志增长。
4. 错波特率、端口占用、USB 转串口瞬断、休眠/唤醒分别验证错误可见且可恢复。
5. 在阶段 C 完成前，任何“参数设置成功”都只能按读回值人工判断，不作为事务成功。

## 6. 修改后复审结论

阶段 A 改动维持了原分层和协议格式；短写仍按偏移续传，发送截止时间只在单帧长时间
未完成时触发，正常背压不会因一次零写被误判。资源所有权路径现在每个 config 只释放
一次。新增校验错误会进入既有无效帧统计，不会导致整个串口断开。

当前代码可作为“可靠串口基础层”的继续演进版本，但在阶段 B/C 完成前仍不能宣称为
工业级闭环控制系统，尤其不能把本地排队成功等同于 MCU 执行成功。
